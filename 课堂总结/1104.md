可靠数据传输的基本模型与问题定义
可靠数据传输是计算机网络中最重要的核心问题之一，甚至被认为是计算机系统领域的"top ten"难题之一。其难点本质上在于：在一个分布式系统中，发送方和接收方要达成一致状态是困难的。

本节课讨论的上下文位于传输层。传统上计算机网络课程自底向上讲授，可靠传输最早在数据链路层的直连链路上研究，但这一机制在传输层同样适用，并且传输层所依赖的网络层正是一个不可靠的信道。因此，可靠数据传输协议的设计目标可以表述为：在不具备可靠性的底层信道之上，通过发送方和接收方各自实现的协议逻辑，向上层提供可靠的数据交付服务。

所谓"可靠"，在本课程中的定义包含两层含义：不丢包和不错包。不丢包指的是数据包不会被丢失；不错包指的是数据包内的比特不会发生错误，即不会出现0变成1、1变成0的情况。

可靠传输协议的建模框架
为了系统化地研究这个问题，需要建立一个抽象模型。模型的基本结构是：发送方进程与接收方进程之间通过一个不可靠信道相连。我们在传输层实现可靠数据传输协议的发送方实现和接收方实现；当发送方需要向下发送数据时，调用底层提供的不可靠发送函数；当接收方从底层收到数据后，经过协议处理，再向上层交付可靠的数据。

从接口角度看，协议涉及四个关键函数：

rdt_send(data)：上层应用调用该函数将数据交给可靠传输层，这是发送方协议实现的入口。
udt_send(packet)：发送方将构造好的数据包通过不可靠信道发送给接收方。
rdt_rcv(packet)：接收方从底层不可靠信道收到数据包时被调用，这是接收方协议实现的入口。
deliver_data(data)：数据经过接收方的可靠性处理后，可靠地交付给上层应用。
核心困难在于：发送方和接收方彼此不知道对方的状态。发送方发出去一个包之后，无法确切知道接收方是否成功正确接收；接收方也无法知道发送方是否了解自己已经收到了包。这种信息不对称只能通过双方交换报文消息来缓解。因此，可靠传输协议的实质是一套精心设计的"状态同步机制"。

有限状态机作为协议描述工具
为了精确描述协议的逻辑，课程使用了有限状态机这一形式化工具。状态机由状态、状态之间的迁移箭弧、触发状态迁移的事件、以及状态迁移时执行的动作组成。一个关键假设是：每个事件引起的状态迁移是唯一的，即从某一状态出发，面对某个特定事件，只能走一条确定的迁移路径。

在后续协议设计中，状态机被用来描述发送方和接收方各自的行为逻辑。对于发送方和接收方，协议做了简化假设：数据流是单向的——只考虑一个发送方向接收方发送数据；但控制流是双向的——确认信息可以在两个方向上传递。这个简化是合理的，因为实际的双向通信可以通过将单向协议在两个方向上各实现一遍来达到。

rdt1.0：可靠信道上的可靠传输
协议设计的起点是最理想的场景：底层信道完全可靠，即不会出现比特错误，也不会丢包。在这种情况下，发送方和接收方的协议极为简单。发送方只需要在收到上层调用时，将数据包装成数据包并通过底层信道发送出去；接收方收到数据包后提取数据内容交付给上层即可。不需要任何额外的确认、重传或检错机制。

这揭示了一个根本原则：底层协议承担的工作越多，上层协议需要做的工作就越少。可靠传输协议的复杂度完全取决于底层信道的不可靠程度。

rdt2.0：处理比特错误——引入确认与重传
当信道可能发生比特错误时，需要引入检错机制。发送方在数据包中加入校验和（checksum），接收方通过校验和来检测收到的数据包是否发生了错误。问题在于：检测到错误之后，如何从错误中恢复？

人类对话中的自然机制提供了启示：当听者没有听清说话者的内容时，会说"什么？请再说一遍"。这种机制在协议中的对应物就是确认机制。具体来说，引入两类控制报文：

ACK（确认）：接收方在正确收到数据包后回复确认。
NAK（否定确认）：接收方发现数据包有误时回复否定确认，发送方收到后重新发送该数据包。
这就构成了确认重传机制。此外，在性能问题尚未提上日程的阶段，协议采用停等协议的做法：发送方发出一个数据包后停止不动，直到收到接收方的确认之后才发送下一个数据包。停等的目的是先确保协议的正确性，设计出一个简单而正确的协议。

发送方的状态机从原来（rdt1.0）的一个状态增加到两个状态：一个是等待上层调用的状态，另一个是发送数据包之后等待ACK或NAK的状态。接收方始终只有一个状态，即等待底层数据包到达的状态。

rdt2.0的关键缺陷在于它没有考虑ACK或NAK本身也可能出错。当发送方收到的反馈报文无法辨认是ACK还是NAK时，问题就出现了。一个看似直观的解决方案是：遇到不确定的反馈就重发当前数据包。但这样会引入新问题——如果接收方实际上已经正确收到了这个数据包，那么重发的包会被接收方当成新的数据包交付给上层，造成重复数据报的错误。

rdt2.1：处理乱码的确认——引入序列号
解决rdt2.0缺陷的方法是为数据包引入序列号。发送方为每个数据包编号，接收方通过序列号来判断收到的包是否早已收到过。在停等协议下，序列号只需要一个比特（0和1）即可。这是因为停等协议中，发送方在任意时刻最多只有一个未确认的数据包在途，所以"当前发送的是编号0还是编号1"就足够区分新旧数据包。

编号引入后，发送方的状态翻倍为四个状态：等待上层调用后发送编号0的数据包、等待对编号0数据包的确认、等待上层调用后发送编号1的数据包、等待对编号1数据包的确认。接收方的状态也翻倍为两个状态：等待接收编号0的数据包和等待接收编号1的数据包。

发送方的状态机工作如下：从初始化状态进入"等待上层调用并发送编号0"的状态；上层调用后，构造带编号0和校验和的数据包发送，迁移到"等待对0的确认"状态；如果收到正确且为ACK的确认，迁移到"等待上层调用并发送编号1"的状态；如果收到NAK或者收到错误的包，则重发编号0的数据包，停留在原状态。等待发送编号1的状态完全对称。

接收方状态机中存在一条容易产生困惑的状态迁移路径：接收方处于"等待接收编号1的数据包"状态时，却收到了一个编号为0的正确数据包。那么这个场景在什么情况下会发生？答案可以通过时序图来说明：接收方已经正确收到了编号0的数据包并回发了ACK，状态也迁移到了"等待编号1"；但由于回发的ACK在传输中发生了错误，发送方误以为编号0的数据包没有成功送达，触发了对编号0的重传。因此，接收方在等待编号1的时候，收到了发送方重传的编号0数据包。此时接收方应当再次回复ACK（确认编号0已收到），状态依旧停留在"等待编号1"，但不能将数据重复交付给上层（因为已经交付过了）。

rdt2.2：无NAK协议
rdt2.1可以进一步简化：完全不需要NAK，只用ACK。这一方案的关键在于改变ACK的语义。在rdt2.1中，ACK表示"这个包收到了"，NAK表示"这个包有错误"。在rdt2.2中，ACK携带具体的序列号，表示"我已经正确收到的最后一个包的编号"。具体说，ACK(n)表示的语义是已经收到了编号为n的包；如果发送方在等待对编号0的确认时收到了ACK(1)，这说明接收方已经收到了编号1的包，但实际上发送方期待的是对编号0的确认，因此需要重发编号0的数据包。

这一设计使得接收方的状态机得到了简化。在等待接收编号0的状态下，出现了两种情况：第一，收到一个错误的包或者收到一个编号为1的数据包（说明发送方在重发错误数据包），此时继续回发ACK(0)，表示"我期待的是编号0"；第二，收到正确的编号0的数据包后，提取数据交付上层，回发ACK(0)，状态迁移到等待编号1。等待接收编号1的状态完全对称。这种设计的应用价值在于：TCP采用的就是这种无NAK的确认方式，它的ACK语义是"我期待的下一个数据包的编号"。

rdt3.0：同时处理错误与丢包——引入超时重传
rdt2.2解决了比特错误问题，但还不能处理丢包。丢包与比特错误的根本区别在于：比特错误时，接收方会回复某种形式的反馈（即使反馈本身可能出错）；而丢包时，发送方不会收到任何反馈——数据包直接消失了。

如何应对没有反馈的情况？答案是超时重传机制。发送方设置一个"合理的"计时器，如果在规定时间内没有收到确认，就认为数据包已经丢失，需要重新发送。这个合理的时间必须包含以下考量：如果数据包或者ACK只是被延迟了而并非真正丢失，重传会导致重复数据包的出现，但序列号机制已经能够处理重复包的问题，接收方可以识别重复包而不重复交付。

因此，解决可靠传输问题的两大核心机制可以概括为：确认重传机制和超时重传机制。rdt3.0在rdt2.2的基础上增加了超时重传能力。

在发送方状态机的"等待对0的确认"状态下，现在存在三种可能的事件：第一，收到正确的、编号为0的ACK，此时停止计时器并迁移到"等待上层调用并发送编号1"的状态；第二，收到错误的包或者收到编号为1的ACK，此时不做任何操作，停留在该状态继续等待；第三，计时器超时，此时重新发送编号0的数据包并重新启动计时器。关键是：在rdt3.0中，只有超时才会触发重传；收到错误或编号不匹配的ACK不会触发重传。

关于rdt3.0正确性条件的关键讨论：rdt3.0需要依赖一个隐含假设——数据包在信道上是按发送顺序到达的，即先发的先到、后发的后到。如果这个假设不成立，即发生乱序到达，rdt3.0协议会出错。可以用TCP中的场景来说明：本来收到了ACK(1)，但因为延迟，发送方重发了编号1的数据包。后来延迟的ACK(1)到达了，发送方误以为编号1的数据包首次被确认，于是发送了编号0。但实际上接收方可能在等待编号1，这时后续的交互会陷入混乱。课程中指出，在链路层这个假设天然成立，因为直连链路上数据包按照先发先到的顺序；但在互联网传输层，底层网络层并不保证数据包的有序到达，因此在传输层实现rdt3.0协议存在出错风险。这阐明了为什么简单的停等协议在传输层还需要后续的完善。

Go-Back-N协议
Go-Back-N（GBN）是管道化协议的一种。其核心特征是滑窗管理和累计确认。

发送方维护一个窗口，窗口大小为 ，表示最多可以连续发送  个未被确认的数据包。发送方维护两个指针：send_base（最早发送但尚未被确认的数据包编号）和 nextseqnum（下一个可以发送的数据包编号）。发送数据时，要求 nextseqnum < base + N。如果 base == nextseqnum，启动计时器。专门为最老的在途数据包设置一个计时器，其他数据包不单独设置。

发送方收到ACK(n)时执行累计确认：ACK(n)表示编号为n及之前的所有数据包都已正确收到。发送方将 base 更新为 。如果此时 base == nextseqnum，即所有在途数据包都已被确认，停止计时器；否则重新启动计时器。

超时处理是GBN高效性的体现：如果超时发生，发送方将重新发送窗口中所有未被确认的数据包——从 base 到 nextseqnum - 1 的全部数据包。

接收方的设计极为简单，只维护一个变量 expectedseqnum。接收方总是发送ACK来确认收到的最高有序数据包编号，这就是累计确认。如果收到乱序的数据包，接收方直接丢弃，不做缓存，然后重新发送对最高有序编号的ACK。这意味着包的丢失会导致后续正确接收的数据包也全部丢弃，发送方必须回退N个包重传，这正是"Go-Back-N"名称的由来。

在一个典型例子中，窗口大小为4，发送方发送了编号0、1、2、3的数据包。如果编号2丢失，编号3到达时接收方因乱序丢弃它，继续发送ACK(1)。发送方收到重复的ACK(1)后忽略。直到编号2的超时发生，发送方重新发送编号2、3以及之后进入窗口的编号4、5。上课时纠正了PPT中接收方状态机的一个细节：在构造待发ACK时，expectedseqnum 应当对应的是等待接收的当前数据包编号，相应位置应该是加一之后的值。

Selective Repeat协议
Selective Repeat（SR）与GBN的核心区别在于：GBN采用累计确认，而SR对每个数据包进行独立确认。接收方正确收到数据包后，针对该数据包单独发送ACK(n)。这意味着接收方有更大的灵活性——可以接受乱序的数据包，将乱序的包缓存下来，等待缺失的包到达后一起进行有序交付。

SR的发送方需要为每个未确认的数据包单独维护计时器。超时发生时，只重发那个导致超时的数据包，而不是像GBN那样重发整个窗口。发送方的窗口同样限制在途数据包数量。当收到窗口范围内的ACK(n)时，将编号n的数据包标记为已接收；如果编号n恰好是最小的未被确认的数据包，窗口向前推进到下一个未被确认的编号。如果ACK(n)的编号在 send_base - N 到 send_base - 1 的窗口之前范围内，可以忽略——这种场景通常源于超时后重复发送导致迟到的ACK。

接收方的窗口设计与GBN不同。接收方维护窗口 [rcv_base, rcv_base + N - 1]。如果收到的数据包编号在该窗口内，回复ACK(n)并将数据包缓存；如果收到的数据包是错序的，也缓存；如果数据包编号在 [rcv_base - N, rcv_base - 1] 范围内，说明是已确认过的重复包，仍然需要回复ACK(n)。当有序的数据包到达时，将窗口向前滑动并交付所有已经有序缓存的数据包给上层。

SR接收窗口的关键约束：接收窗口的大小必须大于等于发送窗口。这是因为如果发送方连续发送了N个数据包，并且最极端情况下最早到达的是编号最大的数据包，接收窗口必须能容纳所有这些编号的数据包。如果窗口小于N，则会出现放不下的问题。

序列号空间与窗口大小的关系是SR协议的一个著名陷阱。考虑序列号空间只有0、1、2、3四个取值，窗口大小为3的情况。场景(a)：发送方发送了编号0、1、2的数据包，接收方全部正确收到并确认，但第三个数据包（编号3）丢失了。随后发送方发送编号0（由于序列号空间循环），接收方窗口已经推进到等待编号3、0、1，因此编号0被窗口接受——这是正常的。场景(b)：编号0、1、2的数据包的数据确实发送成功且接收方正确收到了，但对应的ACK全部丢失。发送方超时重传编号0的数据包。此时接收方窗口已经推进到了等待编号3、0、1，因此编号0被窗口接受——这个编号0的数据包被错误地当成新数据包接收，造成了协议错误。

问题的根源在于：接收方不知道自己收到的编号0是"前一轮的编号0"还是"新一轮的编号0"。接收方的行为在所有场景中看起来完全一样，它无法区分。解决方法是要求序列号空间的大小至少是窗口大小的两倍。这样，当窗口停在某个位置时，窗口之前的编号和窗口之后的编号就不会发生重叠，接收方也就不可能把旧轮的包误认为新轮的包。
