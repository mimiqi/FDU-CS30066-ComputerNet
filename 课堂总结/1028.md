非结构化覆盖网络与结构化覆盖网络
覆盖网络（Overlay Network）构建在应用层之上，其核心特征在于：底层物理网络提供的是黑色实线所表示的互联网连接，而覆盖网络则在主机之间建立虚拟的红色连线，这些虚拟边构成了一个应用层自己的网络拓扑。覆盖网络的虚拟边本质上并不是真正的物理链路，它可能是一条 TCP 连接、一条 UDP 连接，甚至仅仅是一个指向某主机 IP 地址的指针。由于边的虚拟性和松散性，覆盖网络需要周期性地维护：每个节点定期通过 ping 检测邻居节点是否仍然存活，当发现邻居节点失效时，需要建立新的虚拟边来维持网络的连通性。新节点加入网络时同样需要引导过程来建立初始连接。

这种设计带来了显著的灵活性。传统的物理网络一旦部署完成，其链路连接就基本固定下来，而覆盖网络的拓扑结构和维护策略都可以根据应用需求灵活调整。大多数覆盖网络并不考虑物理邻近性，例如一个位于上海的节点，其邻居可能在美国西海岸，两地之间的往返时延大约为 160 到 170 毫秒。不过，部分覆盖网络设计会综合考虑物理距离因素，在建立虚拟边时优先选择 IP 地址邻近的节点，以降低通信时延。

覆盖网络的应用范围非常广泛。DNS 系统本身就可以看作一个覆盖网络，运行 BGP 协议的自制域间路由器之间通过虚拟 TCP 连接构成覆盖网络，CDN 内容分发网络更是典型的覆盖网络实例，应用层组播也是通过覆盖网络实现的。按照拓扑结构的组织方式，覆盖网络可以分为三类：非结构化覆盖网络、结构化覆盖网络以及考虑邻近性的覆盖网络。

非结构化覆盖网络是最早期的 P2P 系统组织形式。以 Gnutella 0.4 为例，新节点加入网络时随机选择三个现有节点作为邻居，所有节点之间的连接都是随机建立的。这种纯随机的拓扑结构导致资源查找只能采用泛洪（flooding）方式：当一个节点需要查找某个资源时，它会向所有邻居节点广播查询消息，每个收到消息的邻居节点再向除消息来源之外的所有邻居转发，如此扩散直到找到目标资源或达到跳数限制。

分布式哈希表（DHT）
结构化 P2P 系统实现定向查找的核心机制是分布式哈希表（Distributed Hash Table, DHT）。DHT 的核心思想是：在应用层和传输层之间添加一个 P2P 子层，该子层由 DHT 实现，构成一个自组织的覆盖网络。每个数据对象（可能是文件本身，也可能是包含文件位置指针的元数据）通过哈希函数映射到一个键值空间中的键 。例如，键值空间可以定义为从  到  的整数区间，也可以使用二维键值空间。每个节点同样在同一个键值空间中拥有自己的标识符。

DHT 提供了简单的 API 接口：应用层程序调用 DHT API，输入数据对象的键 ，API 返回负责存放该键值对应数据的节点标识符。这个节点可能实际存储数据本身，但更常见的情况是只存储指向数据位置的指针或元数据。重要的是，DHT 没有任何集中式节点，所有查询结果都是通过分布式算法在各个节点上协作计算得出的。

BitTorrent 协议
BitTorrent 是 P2P 文件分发的经典应用。文件被划分为 256KB 大小的块（chunk），参与下载同一个文件的节点集合称为一个 torrent。BitTorrent 支持两种节点发现模式：tracker 模式和 DHT 模式。tracker 模式依赖于一个中央的 tracker 服务器来协调节点之间的连接，当新节点 Alice 加入 torrent 时，她首先向 tracker 注册并获取参与该 torrent 的其他 peer 列表，然后开始与这些 peer 交换文件块。DHT 模式则不依赖于中央 tracker，而是通过 Kademlia 协议（在 BitTorrent 中称为 KAD 网络）来定位拥有所需文件块的节点。

在每个时刻，不同的 peer 拥有文件的不同子集。Alice 的处理策略是：周期性地向每个 peer 询问它们拥有的块列表，然后优先请求那些在当前 torrent 中最稀有的块（rarest first），这样有助于在整个网络中保持文件块的均匀分布。

BitTorrent 的核心激励机制是tit-for-tat（以牙还牙）策略。Alice 会从所有正在向她发送数据块的 peer 中选择上传速率最高的四个 peer，向它们发送数据块。其他 peer 则被“choke”（阻塞），暂时不会从 Alice 处获得数据。Alice 每 10 秒重新评估一次前四名。此外，每 30 秒 Alice 会随机选择一个额外的 peer 并“乐观 unchoke”（乐观解除阻塞），开始向它发送数据块。这个机制的目的是打破可能形成的固定搭配僵局：如果始终只与四个高上传速率节点交互，系统中新加入的节点或暂时处于劣势的节点将永远无法获得数据，而乐观 unchoke 给了它们证明自己的机会。如果被乐观解除阻塞的节点表现出足够好的上传能力，它就可能进入 Alice 的前四名，从而形成一个良性循环。这种激励机制鼓励所有参与者积极上传，否则 P2P 网络将退化为少数节点提供资源、多数节点只消耗资源的不可持续状态。

视频流媒体与内容分发网络
视频流和 CDN 是两个独立但紧密相关的概念。CDN 在没有视频流的场景下同样可以存在，例如一般的 Web 内容分发就是 CDN 的经典应用场景。然而，当前几乎所有的视频流都是通过 CDN 提供的，两者的联系因此非常紧密。

视频流的重要性首先体现在流量占比上。根据 2026 年发表的一篇论文中引用的数据，视频流已占全球互联网骨干流量的 70% 以上。其次，用户规模庞大，全球约有十亿级别的视频用户，短视频平台的兴起进一步加剧了这一趋势。第三个挑战是用户的异构性：不同用户的接入方式不同（有线与移动）、带宽能力差异巨大，移动网络的带宽不仅相对较小，还会随时间产生剧烈波动。

视频编码与压缩
视频本质上是一系列以恒定速率显示的图像序列，常见速率为每秒 24 帧或 30 帧。每帧数字图像由像素阵列构成，每个像素用若干比特表示。如果不进行压缩，原始视频的数据量非常庞大。压缩技术主要分为空间压缩和时间压缩两类。空间压缩利用图像内的冗余：例如，当连续  个像素具有相同的颜色值时，不需要逐点发送  个像素值，只需发送颜色值和重复次数两个值即可。时间压缩则利用帧间的冗余：当后续帧与当前帧变化不大时，只需发送差异部分而非完整帧。

根据视频编码速率的性质，可以分为固定比特率（CBR）和可变比特率（VBR）。CBR 的编码速率恒定，而 VBR 的编码速率随着空间和时间压缩程度的变化而变化。这与网络设计密切相关：对于 CBR 视频，网络理论上应该提供恒定带宽保证；对于 VBR 视频，理想情况下网络应该能够根据编码速率动态调整分配的带宽。ATM 网络作为分组交换网的代表，能够提供 CBR 和 VBR 两种服务模型。相比之下，当前的 TCP/IP 互联网设计得相当粗糙，既无法提供 CBR 服务，也无法提供 VBR 服务。互联网的核心设计哲学是网络尽量简单，将复杂的处理放在终端主机上完成，这决定了它不能提供像 ATM 那样的精细服务质量保证。

常见的视频编码标准包括 MPEG 1（用于 CD-ROM，速率 1.5 Mbps）、MPEG 2（用于 DVD，速率 3-6 Mbps）和 MPEG 4（广泛用于互联网，速率从 64 Kbps 到 12 Mbps 不等）。

流式传输与播放缓冲
在理想情况下，视频流传输表现为：服务器以恒定速率发送视频块，网络时延固定，客户端按照录制时的节奏均匀播放。然而实际的互联网传输面临诸多挑战：可用带宽随时间波动（因为多个用户共享网络资源），可能发生数据包丢失和时延抖动。在服务器到客户端的路径上，经过的每一段链路可看作一个管道，不同管道的粗细代表可用带宽的大小，端到端的吞吐量由最细的管道（瓶颈链路）决定。

为了解决这些问题，现代流媒体系统采用播放缓冲（playout buffering）技术。客户端在开始播放前先预先缓存一定量的视频数据。在实际传输中，由于网络抖动，某些视频块的到达时间会延迟较长，甚至形成阶梯状的到达模式。但只要缓冲区中还有预存的数据，播放过程就可以保持均匀、连续的节奏。即使在一段时间内没有新的数据到达，播放也能从缓冲区中继续读取数据，从而补偿网络时延的变化和抖动。这项技术有效改善了用户观看体验。

DASH 协议
当前工业界实际使用的流媒体标准是 DASH（Dynamic Adaptive Streaming over HTTP），即“基于 HTTP 的动态自适应流媒体”。它的核心特点是将流媒体数据的封装交给 HTTP 协议来完成。早期虽然存在 RTP、RTCP 等标准化流媒体协议，但这些协议并未被工业界广泛采纳，而 DASH 则真正成为了事实标准。

DASH 的工作机制如下：在服务器端，视频文件被切分为多个小的 chunk，每个 chunk 以多种不同的编码速率独立编码。不同的编码速率对应不同的视频质量，例如从 144P 到 1080P 的分辨率范围，中间还包含 480P、720P 等不同档位。每种码率的编码结果存放在独立的文件中，并且这些文件（chunk）在全球各地的 CDN 节点上都有副本。服务器还提供一个 manifest file（清单文件），该文件为不同的 chunk 提供对应的 URL，客户端通过 manifest 文件获知每个 chunk 的位置信息。

客户端的行为是关键：客户端周期性估算服务器到自身的可用带宽，然后通过 manifest 文件查询可用的 chunk 列表，选择一个当前带宽条件下能够承受的最高编码速率的 chunk 进行请求。客户端可以在不同时间点选择不同速率的编码，也可能从不同的 CDN 服务器获取 chunk。这种设计的核心思想是将“智能”放在客户端：客户端自主决定何时请求 chunk（以避免缓冲区饥饿或溢出）、请求什么编码速率（带宽充足时请求更高质量）、以及从哪个服务器请求（可能选择距离最近或可用带宽最大的服务器）。因此，完整的流媒体技术路径可以概括为：视频编码 + DASH + 播放缓冲。

CDN 的架构与发展
CDN 解决的核心问题是如何将视频内容或其他内容分发到数百乃至数千个分布在全球的服务器上，以便让数百万并发用户能够高效地访问。如果仅仅使用一台“超大型服务器”向所有用户提供服务，会面临单点故障严重、网络拥塞集中以及远端用户访问路径过长且拥塞等问题。因此，CDN 的基本方案就是在全球范围内分布式地部署服务器，将内容的多个副本存储在多个地理位置分散的节点上。

两个最具代表性的 CDN 运营商是 Akamai 和 Limelight，它们分别代表了两种不同的 CDN 架构哲学。Limelight 的方案更为传统，被称为 “bring home” 策略：它与大型互联网服务提供商紧密合作，在运营商的骨干网络节点中部署大规模的服务器集群（cluster）。Limelight 在全球约有二十多个这样的 POP（Point of Presence）节点，每个节点的计算能力和分发能力都非常强大。由于 Limelight 与运营商关系密切，它在大型体育赛事等场景下能够协助分发视频资源。Limelight 的主要客户群体是视频服务商，中国央视也是 Limelight 的合作方之一。

Akamai 的策略则截然不同，被称为 “enter deep” 策略：它采用“蚂蚁搬家”的方式，将大量小型服务器尽可能深地部署到各个接入网络边缘。Akamai 的服务器数量从 2022 年的 32 万多台增长到 2026 年的 36.5 万台，分布在全球 135 个国家。这些服务器分散在网络边缘，数量庞大但单点能力相对较小。Akamai 最初的业务主要面向 Web 内容（小文件）的分发，而非大型视频文件，但现在也已进入视频分发领域。值得注意的是，Limelight 最近也收购了一家名为 EdgeCompute 的公司，开始发展边缘服务器业务，呈现出向 Akamai 模式靠拢的趋势。两种技术路线正在相互融合。

CDN 本质上是一个覆盖网络。将分布在全球的 CDN 服务器从互联网中“剥离”出来单独观察，它们之间通过虚拟连接构成了一个覆盖在互联网之上的网络。CDN 需要解决的核心问题与 P2P 和 DHT 解决的问题完全一样：将内容放置在哪个 CDN 节点中，以及客户端应该从哪个 CDN 节点检索内容。区别在于，P2P 网络中的节点会动态加入和离开，而 CDN 的服务器由单一组织管理，具有稳定性。这种差异使得 CDN 的解决方案与 DHT 有所不同。

OTT 内容分发与 DNS 重定向
OTT 是 “over the top” 的缩写，意为在应用层之上完成所有事情，不依赖底层网络的特殊支持。OTT 的核心挑战是在拥塞的互联网上从“边缘”实现高效的内容分发。具体问题包括：将什么内容部署到哪个 CDN 节点、客户端应从哪个 CDN 节点获取内容以及采用多大的速率获取内容。

CDN 定位资源的经典方法是 DNS 重定向。以一个具体场景为例：用户 Bob 请求视频 URL http://netcinema.com/6Y7B23V，但实际存储视频的位置是 CDN 节点 http://KingCDN.com/NetC6y&B23V。DNS 重定向的过程是：Bob 首先访问 netcinema.com 的 Web 页面，该页面提供了视频的 URL 地址。Bob 本地的 DNS 服务器在解析该 URL 时，首先查询 netcinema.com 的权威 DNS 服务器，该服务器返回的结果是一个 CNAME（规范名称）记录，指向 KingCDN.com。Bob 的本地 DNS 服务器转而查询 KingCDN.com 的权威 DNS 服务器，最终获得一个具体的 CDN 服务器 IP 地址。Bob 随后直接访问该 CDN 服务器获取视频资源。整个过程中，DNS 的重定向机制使客户端无需知道内容的具体存储位置，由 CDN 的 DNS 服务器根据网络状况和用户位置返回最合适的服务器地址。

另一种资源定位方式是通过 manifest 文件实现。Netflix 的 OpenConnect CDN 是这种方式的典型代表。Netflix 在全球的 OpenConnect CDN 节点上存储内容的副本。当用户订阅内容并请求观看时，服务提供商的 Web 服务器返回一个 manifest 文件。客户端通过 manifest 文件中的信息，选择可支持的最高速率的副本进行内容获取。如果在观看过程中网络路径发生拥塞，客户端可以切换不同的编码速率或从不同的 CDN 节点获取内容。

传输层概述
应用层的学习至此告一段落。应用层中网络特色最鲜明的内容包括：HTTP 协议的持久性与非持久性连接、HTTP/2 和 HTTP/3 的演进、FTP 的双连接机制，以及 P2P 网络中的 DHT 技术。DHT 尤其重要，因为它能够在没有中心节点的对等网络中，实现资源对象的高效定位，查找效率达到  量级。

传输层和网络层是计算机网络的核心。传输层协议提供的是逻辑通信服务：在两个不同主机上的应用进程之间建立一条逻辑信道。这条信道的两端分别连接到两个主机上的进程（通过 socket 实现），发送方将应用层消息分割成 segment（段），加上传输层头部后交给网络层；接收方从网络层接收 segment，去掉头部后将数据重组为应用层可理解的消息，通过 socket 交付给正确的应用进程。socket 是应用层与传输层之间的服务访问点。

传输层面临的一个关键问题是复用与解复用：由于多个应用进程（如 HTTP、FTP、DNS 等）共享同一个传输层协议，发送方需要将多个进程的数据复用到底层网络，接收方需要根据头部信息将收到的数据正确地分发（解复用）到对应的进程。

互联网提供了两个主要的传输层协议：TCP（Transmission Control Protocol）和 UDP（User Datagram Protocol）。TCP 提供可靠的、按序的交付服务，具备拥塞控制、流量控制和连接管理功能。当应用层将消息交给 TCP 后，可以确信数据将以正确的顺序、无差错地到达对端应用进程。UDP 则提供不可靠的、无序的交付服务，它不保证数据一定能到达、也不保证到达顺序，可能出错。UDP 本质上是在 IP 之上几乎没有添加任何有用的功能，仅仅是一种“尽力而为”（best effort）的服务。

UDP 存在的价值可以从几个层面理解。从直接的技术层面看，UDP 不需要建立连接，因此避免了 TCP 连接建立所需的一个 RTT 时延，速度更快；部分应用（如流媒体、DNS 查询）能够容忍数据包的丢失，因此适合使用 UDP。从更深层次看，互联网的设计初衷（源于 ARPANET）是即使在核战争导致部分网络设施被破坏的情况下，网络仍然能够工作。UDP 的每个数据包独立转发，不依赖连接状态的维护，这正是互联网可用性设计哲学的体现。从现代发展的角度看，UDP 的“无用”留下了极大的灵活性空间。由于 TCP 实现在操作系统内核态，用户无法修改，而 UDP 相对简单，用户可以在用户态基于 UDP 构建新的传输协议。QUIC 协议（最初由 Google 开发，后来成为标准）就是基于 UDP 实现的，它把 TCP 的可靠传输、拥塞控制等功能全部在用户态重新实现了一遍，并加上了 TLS 安全支持。HTTP/3 就运行在 QUIC 之上。这正是 UDP 作为“留白”的巨大价值。

从服务模型的角度看，互联网的传输层协议不提供时延保证，也不提供带宽保证。相比之下，ATM 网络能够同时提供 CBR 和 VBR 服务，保证时延和带宽。这体现了互联网设计哲学的核心：网络尽量保持简单，将复杂的功能放到终端主机上的应用层去实现。CS 背景的设计者主导了互联网的设计，这与由电信背景主导的 ATM 形成了鲜明对比。

复用与解复用
基本原理
复用（multiplexing）是指发送方将来自多个应用进程的数据统一交给传输层处理，加上传输层头部（后来用于解复用）后发送到网络层。解复用（demultiplexing）则是接收方根据传输层头部中的信息，将收到的 segment 分发到正确的 socket。

实现解复用的关键在于传输层头部和网络层头部中的四个字段：源端口号、目标端口号、源 IP 地址和目标 IP 地址。每个 IP 数据报的头部包含源地址和目标地址字段（各 32 位），每个 TCP/UDP segment 的头部包含源端口号和目标端口号字段（各 16 位）。这四个字段共同构成了一个标签系统，用来对数据段进行分类并确定应该交给哪个应用进程。

无连接的解复用（UDP）
UDP 的解复用只依赖两个字段：目标 IP 地址和目标端口号。当主机收到一个 UDP segment 时，首先检查目标 IP 地址是否与自身地址匹配，然后根据目标端口号将数据交给绑定了该端口号的 socket。

以具体的例子来说明：假设一台服务器进程绑定端口 6428，两台客户端分别绑定本地端口 9157 和 5775。当服务器发送数据给左侧客户端（目标端口 9157）时，左侧客户端收到后根据目标地址匹配和目标端口号 9157 将数据交给绑定该端口的 socket。当右侧客户端（源端口 5775）向服务器（目标端口 6428）发送数据时，服务器根据目标端口 6428 将数据交给服务器进程的 socket。

UDP 解复用的关键特性在于：具有相同目标端口号但不同源 IP 地址或源端口号的 UDP 数据报都会被导向同一个 socket。这也意味着服务器进程无法从传输层层面区分数据来自哪个客户端，如果需要在应用层区分不同客户端，必须由应用程序自行处理。

面向连接的解复用（TCP）
TCP 的解复用需要依赖完整的四元组：源 IP 地址、源端口号、目标 IP 地址和目标端口号。一个 TCP socket 由这个四元组唯一标识。

UDP 协议
UDP 是一个极其简单的传输层协议，被称为“no frills”（不加修饰）或“bare bones”（裸骨）协议。它提供的是尽力而为的服务：UDP segment 可能丢失，可能乱序到达应用层，也可能出错。UDP 是无连接的，发送方和接收方之间不需要握手，每个 UDP segment 独立于其他 segment 被处理和转发。

UDP 的优势包括：不需要连接建立，因此没有 RTT 时延开销；发送方和接收方没有连接状态需要维护，实现简单；头部很小，只有 8 个字节；没有拥塞控制，UDP 可以按照应用所需的速率发送数据，不受拥塞控制机制的约束。这种特性使 UDP 在拥塞发生时仍然能够工作，而 TCP 会主动降低发送速率。

当前使用 UDP 的主要应用包括：流媒体应用（可以容忍丢失，但对速率敏感）、DNS（仍然主要以 UDP 为主，尽管有 DoT 和 DoH 等加密变体，但传统 DNS 使用最广泛）、SNMP（简单网络管理协议）、以及 HTTP/3。HTTP/3 基于 QUIC 协议，QUIC 又基于 UDP 实现。QUIC 在 UDP 之上实现了可靠传输、拥塞控制和安全功能（TLS 加密），相当于在 UDP 的“留白”之上重新实现了一套增强的传输协议。RFC 768 是 UDP 的标准文档，篇幅很短，大约只有 2.5 页，值得同学们查阅。

UDP 的报文格式
UDP segment 的结构非常简单：数据部分之前是一个 8 字节的头部。头部包含四个字段：源端口号（16 位）、目标端口号（16 位）、长度字段（16 位，表示整个 UDP segment 的长度，包括头部在内，以字节为单位）和校验和（16 位）。

校验和
校验和的目标是检测 segment 中出现的比特错误。UDP 的校验和计算方式如下：发送方将 UDP segment 的内容（包括 UDP 头部）和从 IP 头部中提取的源 IP 地址、目标 IP 地址等信息合并，将整个内容看作一串 16 位整数序列，对这些整数做二进制反码加法（one's complement addition），最终结果取反码后作为校验和放入 UDP 头部的 checksum 字段。具体来说，提取 IP 头部中的源地址（4 字节）、目标地址（4 字节）以及 IP 头部第一行（4 字节），加上 UDP 头部和数据部分，统一按 16 位整数进行加法运算。

二进制反码加法的关键规则是：当加法过程中最高位产生进位时，需要将该进位加到结果的最低位上（回绕，wraparound）。例如，两个 16 位整数相加时，如果最高位产生了进位 ，这个  被回绕加到最后一位上，然后对最终结果取反码得到校验和。

接收方收到 UDP segment 后，采用同样的方法计算校验和，并与收到的校验和字段值进行比较。如果计算结果与校验和字段不一致，说明数据在传输过程中出现了错误，接收方丢弃该 segment；如果一致，则大概率没有出错，但不能完全排除出错的可能。

UDP 校验和是一种较弱的错误检测机制。例如，两个 16 位整数中分别有多个比特同时发生翻转，最终加法结果可能恰好不变，校验和就检测不出错误。这是因为校验和没有严格的理论保证，它主要能够检测单个比特的跳变（如从 1 变为 0），但对于复杂的多位错误可能失效。相比之下，以太网中使用的 CRC 校验码具有坚实的数论理论基础，能够确定性地检测出特定数量的比特错误，是一种更强有力的差错检测手段。

总结来说，UDP 是“尽力而为”的协议，它提供了最小的传输层功能：没有连接建立、没有状态维护、头部极小、没有拥塞控制。它的优势在于：无 RTT 延迟、在网络遭受破坏时仍能工作（满足互联网最初的可用性设计目标）、并且通过校验和提供基本的数据完整性检查。从更广阔的视角看，UDP 的简单性为后续协议的创新留下了空间，QUIC 和 HTTP/3 正是利用这一空间在应用层实现了更先进的传输功能。
