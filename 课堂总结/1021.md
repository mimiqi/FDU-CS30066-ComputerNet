FTP协议：控制连接与数据连接的分离
FTP（File Transfer Protocol，文件传输协议）的任务是实现主机与远程主机之间的文件传输。它采用客户端/服务器模型：客户端发起文件传输请求，可以从服务器下载文件，也可以向服务器上传文件；服务器端则负责存储文件并响应客户端请求。FTP协议的正式规范编号为RFC 959，服务器默认监听21号端口。与HTTP相比，FTP出现得更早，但其核心交互同样基于ASCII字符命令，因此可以直接通过命令行或专用客户端软件进行操作。

FTP最重要的特点在于它在一次通信过程中会建立两条TCP连接：一条控制连接和一条数据连接。客户端首先向服务器的21号端口发起TCP连接，该连接即为控制连接。控制连接建立后，客户端通过它完成用户身份认证、切换目录、列出目录文件等控制操作。服务器在控制连接上会维持一系列状态信息，例如当前用户身份、用户所处的当前目录等。这一点与HTTP形成鲜明对比：HTTP是无状态协议，而FTP服务器必须保存连接状态，因为后续的 LIST、RETR 等命令都依赖于“当前用户在哪个目录下”这一上下文。

当客户端发出文件传输命令后，服务器的行为与普通CS模式应用不同。在传统模式中，服务器会主动从其20号端口向客户端发起第二条TCP连接，这就是数据连接。数据连接专门用于文件数据传输，不承载控制信息。因此，FTP的控制信息与数据信息在两条独立的连接上传输，这种方式称为带外控制，即控制连接位于数据传输通道之外。文件传输完成后，服务器会关闭数据连接，而控制连接通常保持打开状态，直到用户退出会话。FTP传输的文件格式主要有两类：二进制文件和ASCII编码文件。

由于传统模式下数据连接由服务器主动向客户端发起，这在企业网络或校园网环境中会引发防火墙配置问题。一般情况下，内网防火墙对外部主动发起的入站连接采取严格过滤策略，服务器主动连接内网普通客户机的行为会被防火墙拦截，导致数据连接无法建立。为解决这一问题，FTP引入了被动模式。在被动模式下，客户端首先在本地开启两个大于1023的非特权端口，假设分别为  和 。客户端使用端口  连接服务器21号端口，随后在控制连接上发送 PASV 命令。服务器收到该命令后，会选择一个大于1023的随机端口 ，并将该端口号通过控制连接返回给客户端。客户端随即使用本地端口  向服务器的端口  发起第二个TCP连接，即数据连接。这样，两条连接均由客户端主动发起，从而避开了防火墙过滤入站连接的问题。当前大多数FTP应用均采用被动模式。

FTP的控制连接上使用常见的ASCII命令，例如：

USER username：提交用户名；
PASS password：提交密码；
LIST：列出当前目录下的文件列表；
RETR filename：下载文件；
STOR filename：上传文件。
服务器的返回也采用类似HTTP的状态码形式，例如：

331 Username OK, password required：用户名正确，等待密码；
125 data connection already open; transfer starting：数据连接已打开，开始传输；
425 Can't open data connection：无法打开数据连接；
452 Error writing file：写入文件出错。
FTP设计的核心目标是尽量提高文件传输的吞吐量。由于其数据连接中只传输文件数据，因此传输效率较高。不过在现代互联网中，很多应用选择直接在HTTP之上封装数据，通过HTTPS等方式进行文件传输，HTTP/3等新协议也在传输效率和安全方面做了进一步优化。

DNS：作为应用层协议的分布式数据库
域名解析的基本需求
IP地址是互联网网络层用于寻址的标识。IPv4地址长度为32比特，通常写作四个十进制字节的形式，例如 202.120.224.6。虽然这种点分十进制形式已经比原始二进制更方便记忆，但对于用户来说，仍然希望用容易记忆的名称访问主机。域名系统就是为满足这一需求而设计的。用户输入 www.baidu.com 这样的域名，网络系统需要将其映射为实际通信使用的IP地址，这个映射过程称为域名解析。

DNS（Domain Name System）本质上是一个分布式的数据库，分布在全球互联网上，以大量名称服务器构成层次结构。它的核心功能包括：

将主机名映射为IP地址；
将IP地址反向解析为主机名；
实现主机别名解析：一个用户可见的别名可能对应一个完全不同的规范主机名，例如 www.baidu.com 实际对应规范名 ps-other.a.shifen.com，其IP地址为 61.135.162.87；
实现邮件服务器别名解析：邮箱后缀通常是别名，真正的规范邮件服务器名称可能并不直接暴露给用户；
通过多个IP地址对应同一域名，实现负载均衡。
DNS为什么采用分布式结构
DNS没有采用集中式数据库，其原因主要有四点：

首先，集中式结构存在单点故障。顶级域名服务器承载的查询量极为可观，例如Comcast的DNS服务器每天要处理约6000亿次查询，Akamai的DNS服务器每天则要处理约2.2万亿次查询。一旦集中式服务器瘫痪，整个互联网停止工作。实践中，如果用户手动把DNS服务器地址设置为一个不存在的地址，很多网站就会立即无法访问。

其次，集中式结构会面临巨大的流量压力。

第三，集中式服务器距离用户较远，会导致解析时延显著增加。例如从中国访问美国服务器的往返时间可以达到160至170毫秒，解析过程不应承受这样的延迟。

第四，分布管理更符合互联网的自治特性。每个组织应当有权管理自己的域名空间，例如复旦大学管理 fudan.edu.cn 后缀下的主机名分配，而亚马逊公司则管理其 amazon.com 域的解析。

DNS服务器层次结构
DNS服务器大致构成三层逻辑结构。

最顶层是根DNS服务器。根服务器逻辑上只有13个，但每个逻辑服务器在世界范围内被大量复制和镜像，例如美国有约200个实际服务器。根服务器是域名解析的“最后求助对象”，当本地DNS服务器无法从缓存中解析时，才会向根服务器查询。根服务器的主要职责不是直接给出最终IP地址，而是告诉查询方应该转向哪个顶级域名服务器。根服务器的重要性甚至使其成为DDoS攻击的目标，不过历史上针对根服务器的攻击主要通过流量过滤和本地DNS缓存TLD服务器信息两种方式被成功缓解。根服务器管理由ICANN负责。DNS系统的安全加固协议主要包括DNSSEC、DOT和DOH三种。

第二层是顶级域名服务器。TLD服务器分为两类：一类是通用顶级域，例如 .com、.org、.net、.edu 等；另一类是国家顶级域，例如 .cn、.uk、.fr、.ca、.jp 等。不同的TLD由不同机构管理，例如 .com 和 .net 的注册管理机构是NetworkSolutions，.edu 由Educause管理，中国 .cn 域名由CNNIC管理。

第三层是权威DNS服务器。权威服务器是特定域名的最终解释者。例如 amazon.com 的权威DNS服务器由亚马逊自行维护，它提供该域内主机名到IP地址的权威映射。权威服务器可以由组织自行维护，也可以委托服务商维护。

需要特别注意的是，本地DNS服务器并不属于上述层次结构。当主机发出DNS查询时，主机不会直接联系根服务器或权威服务器，而是先向本地配置的DNS服务器发送查询。本地DNS服务器通常由ISP或组织提供，例如在Windows系统中使用 ipconfig /all 可以查看本机配置的DNS服务器地址。本地DNS服务器会首先检查本地缓存中是否已有对应的名称到地址映射，若有则直接返回；若没有，再代表主机进入DNS层次结构进行解析。

迭代查询与递归查询
假设主机位于 engineering.nyu.edu，希望查询 gaia.cs.umass.edu 的IP地址。解析过程存在两种模式。

在迭代查询模式中，本地DNS服务器首先联系根DNS服务器。根服务器不会直接给出最终答案，而是返回一个提示：负责 .edu 顶级域的TLD服务器是哪一台。本地DNS服务器再联系该TLD服务器，TLD服务器返回负责 umass.edu 域的权威DNS服务器地址。本地DNS服务器接着联系权威服务器，最终获得 gaia.cs.umass.edu 的IP地址。每一轮查询中，被联系的服务器只返回“下一步应该找谁”，查询负担由本地DNS服务器承担。

在递归查询模式中，根服务器收到本地DNS服务器的请求后，不再只返回提示，而是自己继续向TLD服务器查询，TLD服务器又继续向权威服务器查询，最终将解析结果逐级返回给本地DNS服务器，再由本地DNS服务器返回给请求主机。递归模式类似于调用一个函数，调用方只需要等待最终结果，不需要关心中间过程。但这种模式下，上层服务器的负担会明显加重，因此实际网络中大量使用的是迭代模式，递归模式仅在本地DNS服务器与客户端之间以及少数支持递归的服务器之间使用。无论采用何种模式，主机与本地DNS服务器之间的第一步总是递归请求，主机本身永远不会直接向根或TLD服务器发出查询。

缓存机制
在解析过程中，每一级名称服务器都会将学到的映射缓存起来。当其他查询再次请求相同域名时，服务器会立即返回缓存结果，从而缩短响应时间。缓存条目会在一定时间后过期，这个时间是TTL字段决定的。典型的TLD服务器信息会被本地DNS服务器长期缓存，这样本地服务器在许多情况下无需访问根服务器即可完成解析。但缓存可能造成数据过期，例如域名对应的IP地址已经发生变化，而缓存中仍然是旧值，则可能返回不准确的解析结果。因此DNS的名称到地址翻译本质上是一种尽力而为的服务，并不保证始终与实时状态一致。

DNS报文格式
DNS查询报文和应答报文结构相同，都由报文头和四个字段数量说明部分组成。报文头由12字节构成，其中前两个字节是标识字段，用于将查询与对应应答匹配；接着是两个字节的标志位。在标志位中，第0位标志该报文是查询还是应答；还包括是否希望递归、服务器是否支持递归、应答是否来自权威服务器等信息。

报文头之后是四个统计字段，每个字段占两个字节，分别表示：

#questions：查询问题数；
#answer RRs：应答资源记录数；
#authority RRs：权威资源记录数；
#additional RRs：附加资源记录数。
问题部分包含要解析的名称及其类型，一般包括类似于 www.163.net: type A, class IN 的记录。应答部分返回查询结果，例如 www.163.net: type A, class IN, addr 118.103.150.80。权威部分列出权威DNS服务器名称，附加部分则常常包含这些权威DNS服务器自身对应的A记录，以方便客户端继续访问。

在实际抓包中，一个典型的对 www.163.net 的查询报文和应答报文具有相同的Transaction ID，例如 0x7044。查询报文的Flags为 0x0100，表示它是查询；应答报文的Flags为 0x8180，表示它是标准应答。应答报文中可能包含1条Answer RR、3条Authority RR和10条Additional RR。这种结构使DNS解析流程清晰直观，建议同学们通过Wireshark等工具抓取本地DNS查询包来加深理解。

DNS的安全问题
传统DNS基于UDP协议运行，端口53。选择UDP的主要原因是为了提高效率。UDP不需要三次握手，一次查询和一次应答即可在一个往返时间内完成；而TCP需要建立连接，开销较大。同时UDP连接不维护状态，服务器负担也较轻。但UDP并不提供数据可靠性保证，更重要的是，传统DNS报文以明文ASCII形式传输，极易被网络攻击者截取、篡改或伪造，造成DNS缓存投毒和欺骗攻击。

针对DNS的安全攻击主要有两类。一类是DDoS攻击，攻击者向根服务器或TLD服务器发送大量流量，试图使其瘫痪。但由于流量过滤和本地DNS缓存机制，攻击通常难以成功。另一类是欺骗攻击，攻击者拦截DNS查询，向客户端返回伪造的应答，导致客户端连接到错误IP地址，进而可能造成网络瘫痪。

为增强DNS安全性，出现了三种安全协议：

DNSSEC：工作在DNS层，通过对DNS解析结果进行数字签名来保证报文完整性，防止结果被篡改；
DOT：即DNS over TLS，将DNS报文通过TLS安全传输；
DOH：即DNS over HTTPS，将DNS查询封装为HTTPS流量，使网络监听者无法区分其中的DNS行为。
三者的协议栈结构不同。传统DNS直接运行在UDP之上；DNSSEC仍在UDP之上的DNS层实现；DOT在传输层使用TLS承载DNS；DOH则在HTTP层之上承载DNS，HTTP又依赖TLS，底层可能是TCP或UDP。需要注意的是，虽然安全DNS正在发展，但目前传统明文DNS仍占据主流，加密DNS尚在逐步推广之中。

P2P应用：原理与架构
什么是P2P架构
P2P架构与客户端/服务器架构的根本区别在于：P2P系统中不存在永远在线的中心服务器，任意端系统之间可以直接通信。每个节点既可请求服务，也可向其他节点提供服务，即同时扮演客户端和服务器的角色。P2P的一个重要性质是自可扩展性：新加入的节点不仅带来新的服务需求，也带来新的服务容量。节点的加入和离开具有间歇性，IP地址也可能发生变化，这对系统管理提出了挑战。

P2P应用类型广泛，包括：

文件共享：如Napster、Gnutella、KaZaA、BitTorrent等；
P2P通信：即时消息、VoIP等，例如Skype在呼叫建立后可以绕过服务器实现节点间直接通信；
视频流分发：例如TikTok采用PCDN技术，将内容分发网络与P2P流量分发结合；
P2P计算：如SETI@home；
分布式哈希表：这是本节课重点讨论的内容方向；
无线自组织网络：其中传感网络非常典型。
文件共享P2P架构的演化
最早的P2P文件共享系统是Napster。虽然文件传输在节点之间直接进行，但Napster仍然保留一个集中式目录服务器。当一个节点连接系统时，会向中心服务器上报自己的IP地址和拥有的文件内容。需要下载文件的节点向中心服务器查询，获得哪个节点拥有目标文件后，直接与其他节点建立连接完成文件传输。Napster的资源目录是集中式的，因此存在三大问题：单点故障、性能瓶颈和版权侵权。这些因素最终导致Napster被关停。

纯粹P2P的典型代表是Gnutella。Gnutella没有任何中心服务器，所有节点完全对等。节点通过与其他节点建立TCP连接来形成覆盖网络。所谓覆盖网络，是在应用层构建的逻辑网络，其边不是物理链路，而是主机之间的TCP连接。一个节点通常与不到十个覆盖网络邻居相连。当一个节点需要查找资源时，会向所有邻居发送查询消息，邻居再向除来源方向之外的所有邻居转发，查询请求如洪水一般在整个覆盖网络中扩散，这就是查询泛洪。找到资源后，资源所在节点与请求节点之间直接通过HTTP进行文件传输。查询泛洪存在可扩展性问题：消息开销随着网络规模增长而变得非常大。

从资源目录和内容存储两个维度来看，P2P架构可以分为三类。第一类是资源目录集中、内容分布式存储的系统，例如Napster和带tracker的BitTorrent。第二类是资源目录和内容都完全分布式的系统，例如Gnutella以及基于DHT的BitTorrent。第三类是混合式系统，例如Kazaa和比特币。比特币网络中存在全节点和SPV节点，全节点保存完整账本并具有完整功能，SPV节点只进行轻量级操作，这类结构介于集中与分布式之间。

覆盖网络
覆盖网络是构建在物理网络之上的应用层逻辑网络。在底层物理网络中，节点是路由器和交换机，边是物理链路。在覆盖网络中，节点是主机，边是主机之间的TCP连接或指向IP地址的虚拟指针。例如在Gnutella中，如果节点  和节点  之间存在一条TCP连接，就认为它们在覆盖网络中有一条边。覆盖层的出现使得我们可以在不改变底层网络结构的前提下，在应用层灵活构建通信拓扑。

覆盖网络需要维护机制。节点会周期性通过ping确认邻居是否仍然存活，或者在通信过程中间接检验邻居状态。如果邻居失效，节点需要建立新的边。新节点加入覆盖网络时，需要先与现有某节点建立连接。这些机制是后续讲解P2P网络自组织、资源定位等内容的基础。
