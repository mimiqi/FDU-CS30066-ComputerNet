应用层课程目标与整体框架
应用层是计算机网络自顶向下学习的起点。相比导论部分，应用层的内容更加贴近日常使用，网络抽象程度相对较低，但其中仍然包含若干贯穿后续章节的重要原理。本章的学习目标并不仅仅是记住 HTTP、FTP、DNS 等具体协议，而是理解应用层背后的公共设计模式与服务模型。

从结构上看，本章主要分为两大部分。第一部分是应用层的基本原理，重点包括应用层与传输层之间的关系、传输层为应用层提供的服务模型、客户端-服务器模式与 P2P 模式的区别，以及进程通信和地址命名问题。第二部分是具体应用协议，主要包括 Web 与 HTTP、FTP、电子邮件相关协议、DNS 域名系统、P2P 文件共享以及视频流媒体应用。其中 Web 与 HTTP 是本节课的重点。

应用层协议可以分为开放协议和私有协议两类。开放协议由 IETF 等标准组织通过 RFC 定义，例如 HTTP、SMTP、FTP、DNS，任何实现者都可以按照规范编写互操作代码。私有协议则由企业或开发者自行定义，例如 Skype、QQ 等。开放协议通常使用小于 1024 的保留端口，例如 HTTP 使用 80 端口，SMTP 使用 25 端口，FTP 使用 21 端口，Telnet 使用 23 端口。私有协议可以自行选择端口，但客户端必须事先知道服务器所使用的端口。

应用层应用的两种基本架构
客户端-服务器模式
客户端-服务器模式是最早也是最基本的网络应用组织方式。在这种模式中，服务器通常长期在线，拥有固定 IP 地址，集中部署在数据中心中，以提供可扩展的服务能力。客户端并不需要长期在线，可以间歇性接入网络，甚至可以使用动态 IP 地址。客户端之间一般不直接通信，而是分别与服务器通信。

例如 HTTP、IMAP、FTP 都是典型的客户端-服务器模式。浏览器作为客户端向 Web 服务器发送请求，Web 服务器响应请求并返回网页对象。这种模式的问题在于，当用户规模增大时，服务器必须通过扩展硬件、增加服务器数量来提升服务能力，扩展成本较高。

P2P 模式
P2P 模式，即对等网络模式，取消了永远在线服务器的概念。每个参与节点既可以作为客户端请求服务，也可以作为服务器向其他节点提供服务。从进程角度看，P2P 节点上既运行客户端进程，也运行服务器进程。

P2P 模式的一个重要特性是自扩展性。在客户端-服务器模式下，新增用户只会增加服务需求；而在 P2P 模式下，新增节点在带来服务需求的同时，也带来了新的服务能力。由于 P2P 节点通常是普通个人电脑，因此节点具有间歇性加入和离开的特点，如何管理节点的动态变化是 P2P 网络需要解决的核心问题之一。

早期校园网中曾使用 P2P 方式实现电视直播分发。直播服务器只向少量初始客户端发送数据，初始客户端再作为服务器向后续加入的节点提供直播流。这样即使大量用户同时观看，也不会使中央直播服务器过载。这一做法受到当时卡内基梅隆大学张辉等人提出的应用层组播思想影响。应用层组播不是依赖网络层 IP 组播能力，而是在应用层通过主机之间的转发实现类似组播的效果。

从网络层地址语义看，通信存在单播、广播和组播三种形式。单播的目标地址是一个唯一 IP 地址；广播的目标地址是子网内所有主机；组播的目标地址是一组地址。IP 协议从诞生之初就设计了组播能力，而应用层组播则是在应用层利用普通单播通信模拟组播功能，后来逐渐发展为 P2P 网络的思想来源之一。

进程通信、套接字与进程寻址
网络应用的最终执行单位是进程。同一主机上的两个进程可以通过操作系统提供的进程间通信机制进行通信，而不同主机上的进程则通过交换报文进行通信。发起通信的进程称为客户端进程，等待被联系的进程称为服务器进程。

应用层与传输层之间的接口称为套接字。套接字可以理解为一扇门：发送进程把报文推进自己的套接字门，其余传输工作由底层网络完成；接收进程从自己的套接字门取走报文。应用开发者只负责套接字之上的逻辑，套接字之下的传输、网络和链路层行为由操作系统控制。

仅仅使用 IP 地址只能定位主机，无法定位主机上的具体进程。真正能够唯一定位应用进程的标识是 IP 地址与端口号的组合。例如复旦大学软件学院服务器的 IP 地址之一是 202.120.224.82，而其 HTTP 服务进程使用 80 端口。通过 IP 地址加端口号，客户端才能准确找到对应的服务器进程。

端口号的分配分为保留端口和自由端口。小于 1024 的端口通常由 IETF 分配给公共服务器协议，例如 HTTP 的 80、SMTP 的 25、FTP 的 21、Telnet 的 23。实际部署中也可以使用 8080、3128 等非默认端口，但客户端必须明确知道该端口，否则无法访问。

传输层服务模型与应用需求
应用开发者对传输层服务有若干可能的需求。第一类是数据完整性，即要求数据传输不丢、不错。典型的文件传输、电子邮件、Web 文档访问都属于这一类，必须保证 100% 可靠传输。第二类是吞吐量需求，某些多媒体应用需要最低带宽保证，例如实时音频至少需要 5 Kbps 到 1 Mbps，视频需要 10 Kbps 到 5 Mbps；而传统数据通信应用通常是弹性应用，对吞吐量没有硬性要求。第三类是时间敏感性，实时音视频和交互式游戏通常要求较低时延，例如实时音视频的时延要求为几十毫秒量级。第四类是安全需求，包括加密、数据完整性保护和端点身份认证。

文件传输、电子邮件和 Web 文档都属于典型的数据通信应用，不能容忍数据丢失，但对吞吐量要求是弹性的，对时延也不敏感。实时音视频可以容忍一定程度的丢包，因为少量丢失可能只造成轻微噪声或画面瑕疵，但仍然需要一定的最小带宽，并且时间敏感。流媒体应用由于可以使用本地缓存，因此对时延不够敏感，但仍可容忍少量丢包。交互式游戏对时延非常敏感，对吞吐量有一定要求，对少量丢包可以容忍。文本消息不能丢包，对吞吐量要求弹性，对时延是否敏感则取决于具体场景。

然而，当前传输层能够提供的服务非常有限。TCP 提供可靠传输，即保证不丢包、不错包，并通过流量控制、拥塞控制、连接管理等机制支撑可靠传输。但 TCP 不提供时延保证、最小带宽保证，也不提供安全服务。UDP 则几乎什么也不做，只提供不可靠的数据传输，既没有可靠性，也没有流量控制、拥塞控制、连接管理、时延保证和安全保证。

这种现象源于互联网设计中的端到端原则。网络核心应尽量简单，把更多功能放在端系统上实现。由于假设端系统足够智能，因此网络层和传输层可以保持简单，应用层在需要时自行增加缺失的功能。

常见应用的传输协议选择
文件传输、电子邮件和 Web 文档访问毫无例外地使用 TCP。原因在于它们都属于典型数据通信业务，必须保证数据不丢、不错，而 TCP 正好提供可靠传输。

互联网电话的情况更为复杂。标准组织定义了 SIP 和 RTP 等协议，其中 RTP 通常运行在 UDP 之上。但在实际应用中，广泛流行的 Skype 使用私有协议，可能在 UDP 或 TCP 之上运行，具体取决于场景。流媒体的主流做法并不是直接使用标准 RTP，而是在 HTTP 之上运行 DASH。DASH 由 3GPP 组织提出，其基本思想是在 TCP 之上再通过 HTTP 实现动态自适应流媒体传输。目前 YouTube、优酷等绝大多数视频平台都采用这种方案。

交互式游戏的传输协议也依赖具体场景。对于用户登录、命令等需要可靠性的数据，通常使用 TCP；而在实时对战时，由于 TCP 建立连接需要额外时间，且会因拥塞控制自动降低发送速率，体验不佳，因此实时动作数据通常使用 UDP。例如有信息称王者荣耀可能使用基于 UDP 的 KCP 协议。KCP 是一个国产开源协议，在 UDP 之上改写了类似 TCP 的可靠传输逻辑，同时避免直接使用 TCP 带来的连接建立和拥塞控制减速问题。

从时间线可以看出，TCP 传输前需要先完成连接建立，例如三次握手，之后才能发送数据；UDP 不需要连接建立，客户端有数据即可立即发送。因此对于实时性要求很高的游戏来说，UDP 具有天然优势。应用开发者之所以常在 UDP 上自行叠加功能，是因为 TCP 和 UDP 已经固化在操作系统内核中，普通开发者难以修改，而 UDP 什么也不做，反而提供了最大的改造自由度。HTTP/3 也是在这个思想基础上发展而来。

传输层安全与 TLS
传统 TCP 和 UDP 套接字没有加密能力，早期网络中密码甚至以明文形式传输。为了提供安全服务，目前在应用层与传输层之间插入了 TLS 层。TLS 通过对应用层交给传输层的数据进行加密，为 TCP 连接提供加密、数据完整性和端点身份认证。

TLS 在应用层实现，应用使用 TLS 库，TLS 再调用底层 TCP。现在大多数 Web 访问都使用 HTTPS，即 HTTP over TLS。例如复旦大学主页在几年前还是 HTTP，现在已切换为 HTTPS。HTTPS 已经变成事实上的标准。

本节课不展开讨论网络安全和 TLS 的实现细节。老师预告下学期可能开设信息安全选修课，其中会详细讲解 TLS 协议。TLS 本身内容可以用两个课时讲完，但在讲清楚 TLS 之前，需要花费四五节课补充加密等背景知识。

Web 与 HTTP 基本概念
Web 页面由对象组成，对象可以是 HTML 文件、JPEG 图片、Java applet、音频文件等。一个页面通常由一个基础 HTML 文件以及若干引用对象构成，这些对象可以存储在不同 Web 服务器上。每个对象通过 URL 唯一定位。URL 由主机名和路径名组成，例如 www.someschool.edu/someDept/pic.gif。

HTTP 是 Web 的应用层协议，采用客户端-服务器模型。浏览器作为客户端请求、接收并显示 Web 对象；Web 服务器根据请求返回对象。HTTP 使用 TCP 作为传输协议，客户端向服务器 80 端口发起 TCP 连接，服务器接受连接，随后在 TCP 连接上交换 HTTP 报文。HTTP 是无状态协议，服务器不保存客户端过去的请求历史。无状态的优点是协议简单；如果服务器和客户端需要维护状态，一旦一方崩溃，双方对状态的理解可能不一致，需要额外机制协调。

非持久连接与持久连接
HTTP 连接分为非持久连接和持久连接两种类型。非持久连接的流程是：先建立 TCP 连接，在该连接上最多传输一个对象，然后关闭 TCP 连接。下载多个对象就需要建立多个 TCP 连接。持久连接则允许在单个 TCP 连接上传输多个对象，直到传输完成后才关闭连接。

非持久 HTTP 的响应时间可以用往返时间 RTT 来量化。RTT 定义为一个小数据包从客户端到达服务器再返回客户端的时间。之所以使用小数据包定义 RTT，是为了忽略数据发出链路所需的传输时间，只关注电磁波或信令在网络上传播的往返时间。取回一个对象的总时间包括：一个 RTT 用于建立 TCP 连接，一个 RTT 用于发送 HTTP 请求并开始接收响应，再加上文件本身的传输时间。因此，非持久 HTTP 的单个对象响应时间为 ，其中  为文件大小， 为链路传输速率。

如果一个页面引用 10 张图片，非持久 HTTP 默认要为每个对象建立新的 TCP 连接，因此总时间将远高于单个对象的 。不过，现代浏览器通常会打开多个并行的 TCP 连接来同时获取多个引用对象，因此实际总时间并不简单等于 10 倍单对象时间。但无论并行数量多大，“每个 TCP 连接最多取回一个对象”这一约束仍然成立。

持久 HTTP 允许服务器在发送响应后不关闭连接，后续相同客户端与服务器之间的 HTTP 消息可以继续在该连接上传输。客户端一旦解析 HTML 文件发现新的引用对象，就可以立即发送新的请求。最好情况下，只需要一个 RTT 即可把所有引用对象取回。原因在于客户端可以连续发送多个 GET 请求，而不必等待前一个对象返回。例如客户端拿到基础 HTML 文件后，发现 10 张图片都在同一服务器上，可以连续发送 10 个 GET 请求，服务器按请求到达顺序逐一返回，因此一个 RTT 内即可完成所有对象的请求传输。

持久连接与非持久连接各有优缺点。非持久连接在传完一个对象后立即关闭 TCP 连接，服务器资源可以迅速释放；持久连接保持连接不关闭，服务器需要持续维护连接状态，资源开销更大。当前网页中图片等资源数量众多，持久 HTTP 更适合大多数场景，因此 HTTP/1.1 默认采用持久连接。非持久 HTTP 仍可用于资源受限制的物联网设备等轻量级场景，因为这些设备不希望承担过多的连接维护开销。

HTTP 报文格式
HTTP 报文分为请求报文和响应报文两类，均采用 ASCII 人读格式。报文以行为单位划分，每行以回车换行结尾。头部字段结束后，以空行即两个连续的回车换行表示报头的结束，空行之后是报文体。

请求报文的第一行为请求行，包含方法、URL 和 HTTP 版本，例如 GET /index.html HTTP/1.1。其后是头部字段，包括 Host、User-Agent、Accept、Connection 等。常见请求方法包括 GET、POST、PUT、HEAD。GET 用于取回资源对象。POST 用于向服务器提交表单数据，数据放在报文体中。PUT 用于上传新对象到指定 URL，与 POST 的区别之一是 PUT 通常是幂等的。HEAD 只请求头部信息，不返回对象本身，常用于条件请求。

响应报文的第一行为状态行，包含 HTTP 版本、状态码和状态短语。常见状态码包括：200 OK 表示请求成功；301 Moved Permanently 表示对象已永久移动；400 Bad Request 表示服务器无法理解请求；404 Not Found 表示文档未找到；505 HTTP Version Not Supported 表示服务器不支持该 HTTP 版本。响应头部还包含 Date、Server、Last-Modified、Content-Length、Content-Type 等字段。

HTTP 实验：手动取回 Web 页面
老师演示了使用 nc 命令手动取回 HTTP 页面的方法。对于 Mac 系统，可使用 nc -c -v www.software.fudan.edu.cn 80 建立到 80 端口的 TCP 连接；对于 Windows 系统，可使用 ncat -C。连接成功后，输入如下 HTTP 请求：

GET /index.asp HTTP/1.1
Host: www.software.fudan.edu.cn
输入完成后按两次回车，即可收到服务器返回的完整 HTTP 响应报文，包括状态行 HTTP/1.1 200 OK、头部字段以及 HTML 页面内容。该实验的前提是目标页面不能是 HTTPS，因为 TLS 加密后无法直接在命令行中观察到明文 HTTP 报文。老师强调，学习网络协议时应多动手抓包验证，实际观察协议行为往往比只读课本更直观。

Cookie 与状态维护
HTTP 本身是无状态的，但很多应用需要维护用户状态，Cookie 是实现这一目标的主要机制。Cookie 系统由四个组成部分构成：HTTP 响应报文中的 Cookie 头行、后续 HTTP 请求报文中的 Cookie 头行、用户主机上由浏览器管理的 Cookie 文件，以及 Web 站点后台数据库中的相应记录。

当用户第一次访问某网站时，如果服务器此前未给该用户分配 Cookie，服务器会在响应报文中加入 Set-Cookie 头，例如 Set-Cookie: 1678，并在后台数据库中为该 ID 建立条目。浏览器收到响应后将 Cookie 保存在本地。下次请求时，浏览器自动在请求报文头部携带 Cookie: 1678，服务器即可识别同一用户，并基于历史记录执行相应动作。

Cookie 可以用于授权、购物车保存、内容推荐和用户会话状态维护。例如用户在电商网站浏览过计算机网络教材但未购买，之后再次访问时，服务器可以根据 Cookie 记录向其推送相关教材页面。但 Cookie 也带来隐私问题。网站可以利用第一方 Cookie 跟踪用户在本站内的行为。更严重的是第三方持久 Cookie，它允许跨多个网站跟踪同一用户，即使用户从未主动访问跟踪方网站，也可能被跟踪。

第三方 Cookie 与跨网站行为跟踪
第三方 Cookie 的典型场景是网页中嵌入第三方广告。假设用户首先访问纽约时报网站，服务器向浏览器返回第一方 Cookie，例如编号 1634。该页面中有广告区域，其内容由第三方广告运营商 AdX.com 提供。浏览器在解析页面时发现引用了 AdX.com 的对象，于是向 AdX.com 发送请求。AdX.com 在响应中设置自己的 Cookie，例如编号 7493。此时用户浏览器中就同时保存了 nyimes.com 的第一方 Cookie 和 AdX.com 的第三方 Cookie。

随后，如果用户访问另一个与 AdX.com 有合作关系的网站，例如 socks.com，该网站同样嵌入 AdX.com 的广告内容。浏览器再次访问 AdX.com 时，会携带之前保存的第三方 Cookie 7493。这样 AdX.com 就能知道同一用户在之前访问过纽约时报，之后又访问了 socks.com。进一步地，AdX.com 可以根据这个跨网站浏览历史向用户推送更精准的广告，例如用户曾访问过袜子相关网站，就可能在后续访问纽约时报时被推送袜子广告。

第三方 Cookie 往往在用户不知情的情况下发生。浏览器显示的页面由多个来源的对象组成，用户通常不会意识到页面中的部分内容来自第三方服务器。随着隐私保护的加强，Firefox 和 Safari 已默认禁用第三方跟踪 Cookie，Chrome 也从 2023 年开始禁用。与第一方 Cookie 相比，第三方 Cookie 的关键风险在于它使跨多个网站的共同身份识别成为可能，从而形成对用户浏览行为的持续跟踪。

Web 缓存与代理服务器
Web 缓存又称代理服务器。其目标是尽量在不访问原始服务器的情况下满足客户端请求。用户配置浏览器将 HTTP 请求发送到本地 Web 缓存，如果缓存中已有请求对象，缓存直接返回对象；如果没有命中，缓存向原始服务器请求对象，将响应缓存后返回给客户端，并在后续请求中直接提供该副本。

从协议角色来看，Web 缓存同时充当客户端和服务器。作为服务器，它面向原始请求客户端；作为客户端，它向原始服务器请求对象。正因如此，Web 缓存需要实现完整的七层协议栈，而不是仅仅做链路层或网络层转发。

Web 缓存的主要作用有两方面。一是减少客户端的响应时间，因为缓存通常更接近客户端。二是减少机构接入链路上的流量。对于企业网或校园网来说，热门资源如果在本地缓存命中，就不必反复占用接入互联网的带宽。

条件 GET
为了配合本地缓存，HTTP 提供了条件 GET 机制。如果浏览器已经缓存了某个对象，再次请求时可以发送带有 If-modified-since 头字段的 GET 请求。服务器收到该请求后，如果对象在该日期之后没有被修改，则返回不包含对象主体的 304 Not Modified 响应；如果对象已经修改，则返回正常的 200 OK 响应，并在消息体中携带新对象。

条件 GET 避免了在对象未变化时重新传输整个对象体，从而减少传输时间和带宽消耗。其本质是为缓存一致性提供一个简单而有效的机制。

HTTP/1.1 的队头阻塞问题
HTTP/1.1 引入了持久连接，并允许在同一个 TCP 连接上连续发送多个请求，即流水线化 GET。但服务器通常按先到先服务原则依次处理并响应请求。这种模式存在队头阻塞问题：如果先请求的对象体积较大，后续小对象必须等待大对象传输完成后才能被发送，导致整体传输延迟增加。此外，当某个 TCP 报文段丢失需要重传时，后续对象传输也会被阻塞。

从图中可以形象地看到，若客户端依次请求 O1、O2、O3、O4，且 O1 体积很大，其他三个对象都很小，按照 HTTP/1.1 的 FCFS 规则，O2、O3、O4 只能排在 O1 之后等待，而 O1 长期占用连接，小对象的响应被严重延迟。

HTTP/2 的改进
HTTP/2 由 RFC 7540 在 2015 年定义，其核心目标是减少多对象 HTTP 请求中的时延。HTTP/2 在方法、状态码和大多数头部字段上仍与 HTTP/1.1 保持一致，但在对象发送顺序和服务端灵活性方面做了显著改进。

HTTP/2 允许根据客户端指定的优先级确定请求对象的发送顺序，不再严格遵循先到先服务。服务器还可以主动向客户端推送尚未请求的对象，避免客户端下一次再发起单独请求。更重要的是，HTTP/2 将对象切分为帧，并在帧层面进行交错传输。这样不同对象的帧可以轮流发送，较小对象可以更快完成传输，从而缓解队头阻塞。

在 HTTP/2 图示中，O1、O2、O3、O4 被切分为大小均匀的帧。传输顺序不再是一个对象全部完成后再传下一个，而是 O1 的第一个帧传完后，立即传 O2 的帧，再传 O3 的帧和 O4 的帧，然后回到 O1 继续传输。最终 O2、O3、O4 很快完成，只有 O1 因为文件较大而略有延迟。各对象近似公平地共享 TCP 连接带宽，降低了单个大对象对小对象的影响。

从 HTTP/2 到 HTTP/3
HTTP/2 虽然通过帧交错缓解了应用层的队头阻塞，但仍然运行在单个 TCP 连接上。一旦 TCP 报文段丢失，所有对象传输仍会被阻塞，因为 TCP 的可靠传输要求丢失段重传完成后，后续数据才能继续交付。因此，HTTP/2 仍存在传输层级的队头阻塞问题。

此外，传统 TCP 连接本身不提供加密，安全性需要额外由 TLS 提供。HTTP/3 的目标是在 UDP 之上增加安全性、逐对象错误控制和逐对象拥塞控制。UDP 不强制连接建立和严格可靠传输，使得应用层可以细粒度控制不同对象的传输行为，避免单个对象丢包阻塞所有对象。HTTP/3 的详细机制将在传输层章节进一步讨论。
