# Checkpoint 3：TCPSender 参考讲解

资料入口：[Winter 2024 讲义归档](https://github.com/yyym-y/Stanford-CS144/blob/f6116c31133bf2514db0ae924755520cf3fc236b/file/Lab%20Checkpoint%203-the%20TCP%20sender.pdf)、[RFC 6298 重传计时器](https://www.rfc-editor.org/rfc/rfc6298.html)。实验使用简化规则，不要求自行扩展为完整拥塞控制实现。

## 状态应该怎样拆分

一种便于推演的设计是分别记录：下一个待分配绝对序号、接收窗口、SYN/FIN 是否发过、尚未完全确认的消息队列、初始与当前 RTO、计时器运行状态、累计计时、连续重传次数。消息队列保留每段占用的序号区间。

`sequence_length = SYN占位 + payload字节数 + FIN占位`。纯空消息不占序号，不进入重传队列。不能把“payload 为空”误当成“序号长度为零”。

## push：怎样填充窗口

1. 计算还能发送的序号空间，并检查 SYN 是否需要发送。
2. 从 ByteStream 读取数据，每段 payload 不超过 starter 的 `MAX_PAYLOAD_SIZE`；不要在笔记中的某个数字上写死实现。
3. 只有应用写端关闭、待发送数据已全部取出且窗口仍能容纳 FIN 时，才附加 FIN。
4. 调用该版本提供的发送接口，保存非零长度消息，推进下一个序号。
5. 若还有数据和窗口空间，继续形成下一段；计时器已经运行时，发送后续新段不能让最早未确认段无限延期。

课程的零窗口约定：填窗时把有效额度视为 1，但保存的真实通告窗口仍为 0。已有在途消息占满这一额度时也不能继续无限探测。窗口尚未通告前的初值按该版本讲义为 1。

## receive：怎样处理 ACK

将 ACK 用自己的 ISN 展开到绝对空间，拒绝确认尚未发出的未来数据。队首消息的结束序号不大于 ACK 时，才可把该整段移出未确认队列。重复或陈旧 ACK 不应重复扣减计数。

课程允许部分确认时保留整段，不必截短重传内容。因此在这种模型下，不能随意把“队列保留消息的序号长度之和”替换为 `next_seq - last_ack`：部分确认时两者可能不同。

当 ACK 确认了新数据，按实验规则恢复初始 RTO、清零连续重传次数；仍有未确认数据时重新计时，否则停止计时器。只有窗口更新而 ACK 没有前进时，不应当作新数据确认。RST 的处理跟随本校 starter。

## tick：怎样重传

时间来自 `tick(ms)` 参数，保持测试可重复。计时到期且有待确认消息时，重传最早的一段；真实窗口非零时，连续重传次数加一、RTO 加倍；真实窗口为零时不做这两个增加。之后重新开始计时。

**手算例子：** SYN 已确认，发送数据区间 `[1,4)`，RTO=200 ms，窗口非零且没有 ACK：在 200 ms 时重传，RTO 变为 400 ms；再经过 400 ms 后再次重传，RTO 变为 800 ms。随后收到合法 ACK=4，队列清空、计时停止，RTO 恢复 200 ms。这里只使用绝对序号，实际报文还需 wrap。

## 易错边界与验证

| 情况 | 应检查的答案 |
| --- | --- |
| FIN 恰好放不进窗口 | 等待窗口空间，不能提前占用窗口之外的序号。 |
| 重复 ACK | 不重复删除消息，不重置新数据确认相关计数。 |
| 一个消息只被部分确认 | 允许整体保留，重传时仍从原来的消息开始。 |
| 纯 ACK 搭配的空发送消息 | 使用正确 seqno，但不作为待重传数据。 |
| 零窗口持续很久 | 探测行为和普通超时退避分开处理。 |

执行 `check3`，结合单测逐项验证，不以“能发出一段数据”代表发送方完成。
