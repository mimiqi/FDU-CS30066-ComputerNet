## 第一部分：为什么要重新运行 webget

Check0 使用操作系统 TCP。这里保留 HTTP 应用逻辑，换成封装自己发送方、接收方的 socket，从而检验自己的 TCP 是否能与真实服务器互通。2024 讲义使用 `tcp_minnow_socket.hh` 中的 `CS144TCPSocket`。

参考顺序：先确认原 webget 工作正常，再按该版本要求更换 socket；准备 TUN 环境，重新构建并运行 `check_webget`。TUN 负责让用户态程序读写 IP 数据包，TAP 则读写以太网帧，见 [Linux TUN/TAP 文档](https://docs.kernel.org/networking/tuntap.html)。

2024 讲义从项目根目录使用以下命令准备 TUN：

```bash
./scripts/tun.sh start 144
```

此处是资料记录，使用前需确认自己的 starter 存在该脚本及相同参数；本次没有执行。程序输出正文与诊断日志应分开，避免把调试文字混入网页响应。

### 对常见现象的解释

| 现象 | 应收集的证据 |
| --- | --- |
| 单测通过，但握手失败 | TUN 配置、路由、是否发出 SYN、是否收到 SYN+ACK |
| 握手成功，传输停住 | ACK 是否推进、窗口是否为零、重传计时是否工作 |
| 内容正确但进程不退出 | FIN 的序号、确认、两个方向的结束状态 |
| 程序输出与预期不同 | stdout 中是否混入日志、HTTP 是否完整读到 EOF |

可对照 [PCloud 的亲历记录](https://pcloud.dev/cs144-checkpoint-4/) 理解框架的数据路径；其中遇到的具体环境现象只代表该作者的实验。

## 第二部分：测量问题的解答方法

该部分没有与电脑、网络、时间无关的一套固定数值。以下给出计算方法，数据必须来自实际运行。

Linux ping 的选项说明见 [iputils ping 手册](https://man7.org/linux/man-pages/man8/ping.8.html)。2024 任务先选择从实验机测得 RTT 至少 100 ms 的目标，并用 `mtr` 或 `traceroute` 记录路径，再每 0.2 秒采样一次、持续至少两小时。参考命令如下，`目标主机`需替换：

```bash
ping -D -n -i 0.2 目标主机 | tee ping-data.txt
```

理论发送量为 `5 × 3600 × 2 = 36000`，实际计算应使用真实发送计数。结束时保留 ping 的统计摘要，并给最后发出的请求留下足够等待回复的时间；不能只根据最后一个成功回复的序号推断总发送量，否则会漏算尾部丢失。

### 统一数据模型

令每个已发送请求的结果 `X_i` 为 1（收到至少一个对应回复）或 0（观察结束前没有回复），收到回复时另记 RTT。按请求序号整理、对重复回复去重；丢失样本的 RTT 记为缺失，不能写为 0 ms。

| 问题 | 计算方法 |
| --- | --- |
| 总交付率 | `sum(X_i) / N_sent` |
| 最长连续成功/丢失 | 扫描 1 和 0 的连续段，分别取最大长度 |
| `P(成功下一包 | 本包成功)` | `count(1→1) / count(以1开头的有效相邻对)` |
| `P(成功下一包 | 本包丢失)` | `count(0→1) / count(以0开头的有效相邻对)` |
| 最小/最大 RTT | 在成功且具有有效 RTT 的样本上取极值 |
| RTT 随时间变化 | 横轴为实际时间，纵轴为毫秒 RTT；缺失回复留空，不绘成 0 |
| RTT 的经验 CDF | 对每个横轴阈值 x，计算 `count(RTT ≤ x) / N_valid_RTT` |
| 相邻 RTT 散点 | 仅取序号相邻且双方均成功的样本对 |

分母为零时应报告“无可用样本”，而不是填 0 概率。`i` 与 `i+1` 指原始请求序号相邻，不能删掉丢失记录后把两条不相邻的成功回复硬接起来。

### 手算例子

假设结果序列为 `1,1,0,0,1,1`：交付率为 `4/6`，最长成功段为 2，最长丢失段为 2；有效相邻对中 `P(1|1)=2/3`、`P(1|0)=1/2`。这是自行构造的例子，不是本次联网测量结果。

新版若要求多个时滞 k，可在 `i`、`i+k` 都存在的索引对上计算同样的条件比例。上表中的两种条件交付率都与总体成功率比较；如果改算条件丢失率，再与总体丢失率比较。观察差异可帮助讨论突发丢失，但需结合样本数解释，单次测量不能证明严格独立。
