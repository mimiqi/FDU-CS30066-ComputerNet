# ByteStream 与 C++ 基础

整理日期：2026-10-22。

## 先把接口语义弄清楚

依据 [本地实验说明第 9—10 页](../check0.pdf)：ByteStream 是一个有容量限制、按写入顺序读取的内存字节流。容量约束“此刻写入但尚未移除的字节”，不限制整个运行期间累计传输的数据量。

| 接口或状态 | 需要理解的含义 |
| --- | --- |
| `push(data)` | 只接收当前剩余容量允许的前缀 |
| `peek()` | 查看接下来可读的字节，不移除数据 |
| `pop(len)` | 消费缓冲区前面的字节 |
| `close()` / `is_closed()` | 写入端已经结束 |
| `is_finished()` | 写入端已经关闭，且缓冲区已经读空 |
| `bytes_buffered()` | 当前缓存了多少尚未消费的字节 |
| `bytes_pushed()` / `bytes_popped()` | 累计实际接收和消费了多少字节 |

“暂时没有可读数据”与“流结束”是两个不同状态。关闭写入端时已有的数据仍然需要能够读出。

## 一个手算例子

下面是依据上述接口约定自行构造的示例，用于理解状态变化，不是测试运行结果。设容量为 5 字节；字符串均为 ASCII，因此一个字符对应一个字节。

| 操作后 | 逻辑缓冲内容 | 剩余容量 | 累计写入 | 累计移除 | 已关闭 | 已结束 |
| --- | --- | ---: | ---: | ---: | --- | --- |
| 初始化 | 空 | 5 | 0 | 0 | 否 | 否 |
| `push("abc")` | `abc` | 2 | 3 | 0 | 否 | 否 |
| `pop(2)` | `c` | 4 | 3 | 2 | 否 | 否 |
| `push("defgh")` | `cdefg` | 0 | 7 | 2 | 否 | 否 |
| `close()` | `cdefg` | 0 | 7 | 2 | 是 | 否 |
| `pop(5)` | 空 | 5 | 7 | 7 | 是 | 是 |

第二次 push 只接受 `defg`，剩下的 `h` 没有进入流。由本地接口约定可推导出，在正常操作序列中应保持：

```text
当前缓存量 = 累计实际写入量 - 累计移除量
剩余容量 + 当前缓存量 = 初始化容量
流结束 = 写入端已关闭 且 当前缓存量为零
```

特别注意：调用者提供的数据长度不一定等于实际写入长度；累计计数也不是当前缓冲区长度。

## string_view 为什么需要单独阅读

[C++ 工作草案的 string_view 章节](https://eel.is/c++draft/string.view) 描述了对连续字符序列的视图。它引用已有字符存储；如果底层字符地址失效，视图的相关访问也会失效。

对本实验的启发是：阅读 `peek()` 时，检查返回视图指向谁拥有的数据、数据是否连续，以及哪些后续操作可能使它失效。返回一个指向函数内临时字符串的视图，会留下生命周期问题。不要把“返回了视图”理解成“复制出了一份独立字符串”。这是结合接口与语言规则得出的设计检查点。

## C++ 风格资料

[C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines) 可重点阅读资源管理部分的 R.1、R.10、R.11：利用对象生命周期管理资源，减少手工分配和释放造成的遗漏。对应到 Minnow，应先理解已有 socket、文件描述符封装如何管理资源。

本地课程还要求优先使用标准库字符串、合理使用 const、缩小变量作用域。具体语言版本和可用接口要检查课程 starter 的构建配置。

[C++ 工作草案的 deque 说明](https://eel.is/c++draft/deque.overview) 可用于理解双端增删的容器特性。选择数据结构时还需要考虑如何返回连续的字符视图、复制量以及实际测试性能；本笔记不替实验指定唯一容器。

## 官方 FAQ 中值得保存的问题

[CS144 Lab FAQ 的 Lab 0 部分](https://cs144.github.io/lab_faq.html) 提到：超出缓存长度的 pop 在其课程中允许合理处理；运行耗时和吞吐率也能帮助判断数据表示是否合适。这是 Stanford 的解释，超范围操作在本校版本中的具体约束应核对课程接口、测试或助教答复。

本校 PDF 明确的性能目标是超过 **0.1 Gbit/s**，即 100 Mbit/s，按 8 bit/byte 换算约为 12.5 MB/s（十进制）。测量结果应使用实际 benchmark 输出，不能由容器复杂度推断已经达标。

## 实现前可以自己回答的问题

- 空流但尚未关闭时，读端是否结束？
- 容量已满后 push 更多数据，累计写入量怎样变化？
- close 后仍有数据，读端应该观察到什么？
- 多次少量写入、读取后，总传输量能否超过容量？
- peek 是否改变缓冲区内容或累计计数？
- 空输入、零长度消费和很小容量是否都能一致处理？

这些问题用于澄清语义和准备调试，不是已经通过的测试清单。
