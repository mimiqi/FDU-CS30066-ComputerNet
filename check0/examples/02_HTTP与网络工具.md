## HTTP 原文看哪里

[RFC 9112：HTTP/1.1](https://www.rfc-editor.org/rfc/rfc9112.html) 是协议的一手资料。与本实验最直接相关的是：

- [第 2.1 节](https://www.rfc-editor.org/rfc/rfc9112.html#section-2.1)：消息的行结构与 CRLF。
- [第 3 节](https://www.rfc-editor.org/rfc/rfc9112.html#section-3)：请求行及 Host 要求。
- [第 9.6 节](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.6)：连接关闭。

阅读要点：请求行和各个头部行以 `\r\n` 结束，头部后还需要一个空行。HTTP/1.1 请求需要 Host 字段。客户端发送 `Connection: close` 表示这是本连接上的最后一个请求。

## 对照本校 2.1：手动获取网页

下面的域名、路径和操作来自 [本地 PDF 第 4—5 页](../check0.pdf)。

先运行：

```bash
telnet cs144.keithw.org http
```

连接后逐行输入，最后一行之后再按一次回车，形成空行：

```http
GET /hello HTTP/1.1
Host: cs144.keithw.org
Connection: close

```

这段代码块展示的是阅读形式。将其组织成程序发送的字节时，完整末尾应当是 `Connection: close\r\n\r\n`，不能只发送一个换行。

应该观察到 HTTP 响应状态行、响应头、空行及正文。浏览器会处理响应并显示页面；终端会让你看到收到的原始 HTTP 数据。保存能体现请求和返回结果的实际截图。

## 对照本校 2.2：两个终端通信

本地 PDF 的服务端命令是：

```bash
netcat -v -l -p 9090
```

另一个终端运行：

```bash
telnet localhost 9090
```

在任一终端输入文字并回车，观察另一端收到的内容。这有助于把“监听”“连接”和“双向字节流”对应到实际行为。

Netcat 有不同实现，选项语法可能不同。[OpenBSD 的 nc 手册](https://man.openbsd.org/nc.1) 使用将端口放在末尾的监听形式，例如本实验端口可写为：

```bash
nc -l 9090
```

两种监听命令选一种运行即可。如果参数不兼容，先查看本机 `nc -h` 或 `man nc`，确认安装的是哪个实现，再调整语法。

## 阅读 webget 接口时带着这些问题

下面的问题按 [本地 PDF 第 7—9 页](../check0.pdf) 的任务整理，供阅读 starter 时使用：

1. `Address` 如何表达目标主机与服务？
2. `TCPSocket` 通过哪个接口建立连接？
3. `FileDescriptor` 提供什么读写接口，返回值是什么？
4. socket 如何报告 EOF，如何区分“本次读到的数据”与“整个响应”？
5. 请求中的主机名、路径是否来自程序参数？

本地实验要求读取并输出服务器返回的全部数据，直到 EOF；一次读取不能保证获得完整响应。测试还会使用其他主机名和路径，因此不能把示例地址写死。

## 自查笔记

以下是依据实验要求整理的检查顺序，不代表已观察到的错误：

| 现象 | 优先检查 |
| --- | --- |
| 请求后没有响应 | 请求头末尾的空行、CRLF、Host 是否正确 |
| 返回内容不完整 | 是否只读取了一次或过早退出循环 |
| 一直等待结束 | 是否发送 `Connection: close`，是否正确判断 EOF |
| 示例能运行，测试失败 | 主机名和路径是否写死、是否额外输出了调试文字 |
| netcat 参数报错 | 本机 netcat 实现和帮助信息 |

服务可达性、DNS 和校园网络条件需要在实际实验机上验证。本次保存的是资料和命令，不是联网成功记录。
